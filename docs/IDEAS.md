# IDEAS: идеи для развития

Записываем идеи, которые не входят в текущую спецификацию.

## Расшифровка и нормализация

- **Повторная расшифровка другим ASR-движком (например, Nemotron).** Машинная расшифровка
  местами искажает термины и содержит нечитаемые места; второй движок позволит сравнить
  варианты и выбрать более надёжный фрагмент. В схеме уже есть
  `interview.transcript_source`, поэтому повторная расшифровка не потребует смены модели
  данных. Вне M1.
- **Сравнение версий L2 между движками.** Если появится вторая расшифровка, полезна
  метрика расхождения L1/L2 по репликам, чтобы выбирать движок по данным, а не на глаз.
- **Золотой набор для L2.** 30-50 реплик первого транскрипта с ручной нормализацией:
  даёт метрику «доля принятых без правок» и позволяет проверить, не срезает ли проход
  смысл. Требует ручной работы оператора, поэтому вынесено за рамки текущей задачи.
- **Выборочная проверка ревьюером.** Просмотр всех единиц с флагами плюс случайной доли
  (порог `m1b.review_sample_share`) в интерфейсе сравнения L1 и L2 рядом. Нужны статусы
  «принято / исправлено / отклонено» и замораживание версии (`approved`).
- **Проверка отношения длин L2/L1.** Ориентир 0,6-1,1 из SPEC: ловит и потерю смысла,
  и «переписывание» ответа. Пороги в конфиге уже есть, но метрика не считается, пока
  нет золотого набора для калибровки.
- **Проверка новых смысловых слов по леммам.** Автопроверка 5 SPEC требует `pymorphy3`;
  сейчас её заменяет консервативная проверка названий. Без лемматизации нельзя отличить
  законную словоформу от придуманного слова.
- **Пополнение лексикона из прогонов.** Сейчас `new_term` копит кандидатов, а решение
  принимает `review-terms`. Полезно показывать в отчёте, сколько единиц отклонено
  именно проверкой названий: это прямой сигнал, что лексикон неполон.
- **Точечный пересчёт одного интервью после пополнения глоссария (вариант C).**
  Сейчас `normalize <код> --new-version` пишет новую версию целиком, даже если
  изменился один термин. Точечный пересчёт пересобрал бы только реплики, где
  новая форма реально встречается, а остальные единицы скопировал бы из прежней
  версии. Требует решения, как хранить признак «единица перенесена» и как
  пересчитывать `run_id` и `changes_json`; отложено до первых 3–5 интервью.
- **`structure --rebuild` при наличии аннотаций.** Пересборка фрагментов падает с
  `FOREIGN KEY constraint failed`: `annotation.fragment_id REFERENCES fragment(id)`
  объявлен без `ON DELETE`, а пересборка удаляет фрагменты. Поэтому цепочка
  «пополнить глоссарий → `normalize --new-version` → `structure --rebuild` →
  `code`» на уже размеченном интервью сейчас недоступна. Нужна либо миграция с
  `ON DELETE CASCADE`, либо пересборка без удаления аннотаций. В M7 не чинится:
  схема БД в этой задаче запрещена к изменению.
- **Версионирование лексикона в БД.** `lexicon_hash` в `run.params_json` отвечает
  на вопрос «каким снимком записана версия», но не даёт выбрать снимок при
  повторном прогоне. Отдельная таблица версий лексикона и привязка `text_unit`
  к версии сделали бы воспроизводимость явной ценой миграции. Отложено: схема в
  M7 не меняется.

## Безопасная работа с копией БД

- **Явный выбор базы: `--db` или `QA_DB_PATH`.** Сейчас `Settings.load()` читает
  `config.yaml`, `config.local.yaml` и окружение только для LLM-полей и
  `QA_DOMAIN_HINT`; `DB_PATH` не поддерживается. Из-за этого запуск
  `DB_PATH=/tmp/copy.db qa-pipeline normalize ...` молча работает по
  `paths.db: data/db/interviews.db` — так произошёл инцидент 2026-11-12
  (140 строк в `new_term` рабочей базы, откат выполнен). Предлагается добавить
  в `Settings.load()` чтение `QA_DB_PATH` с приоритетом над `paths.db` (как у
  `QA_DOMAIN_HINT`) и/или общую опцию `--db` у подкоманд, работающих с БД.
  Правка небольшая и вне M7: одна ветка в `Settings.load()`, одна опция в
  `build_parser()`, тест на приоритет. Не реализуется без решения оператора
  (CONSTITUTION §1.4). До появления опции проверки на копиях запускаются только
  скриптом, который открывает копию явным путём.

## Часть B: работа с неизвестными кандидатами (первая задача)

- **Кластеризация кандидатов `new_term` по фонетической близости.** Созвучные варианты
  одного слова («Сенжин», «Всенж», «Усеннджин») сейчас идут отдельными кандидатами,
  и оператор утверждает каждый по очереди. Предлагается: транслитерация в общий алфавит,
  нормализация согласных, расстояние по `rapidfuzz`, кластеры показываются оператору
  одним блоком и утверждаются одним действием. Решение всё равно принимает человек —
  кластеризация только сокращает число шагов. Зависимость `rapidfuzz` требует обоснования
  в SPEC (CONSTITUTION §2).
- **Нечёткое сопоставление с лексиконом — только после кластеризации.** Кандидаты
  передаются модели как подсказка («возможно, это вариант термина X»), а не как
  автозамена: модель не угадывает, решение фиксируется через лексикон. Порог подбирается
  на размеченной выборке.

## Разметка M2

- **Две аннотации вместо одной для кодов A3/4.** Код A3/4 в текущем кодбуке не различает
  подвиды ответственности, поэтому предлагается ставить по нему две аннотации с признаком
  «не различает»: расхождение внутри кода видно в отчёте и не теряется при агрегации.
  Требует уточнения на пилоте, в M1 не входит.
- **Общий признак «код не различает подтипы».** Механизм вместо отдельного правила для
  A3/4: поле у кода, помечающее, что код агрегирует несколько смыслов.
- **Оценка понимания (верно / частично / неверно по фактам Финама).** В M2 не входит.
  Нужен эталон Финама по вопросам 6, 7Т, 11, 14, 19, 20 и заполнение `reference_fact`;
  отдельный промпт и ручная сверка. Оценка в тот же вызов кодирования дешевле по
  вызовам, но смешивает оценку факта с кодом и рискует опереться на прочтение
  искажений моделью. Варианты и стоимость — в `specs/SPEC-M2.md`, открытый вопрос 4.
- **Кластеризация фрагментов с кодом `OTH`.** В M2 все `OTH` уходят в ручную проверку
  поштучно; при заметной доле `OTH` полезно группировать их по смыслу (эмбеддинги,
  M3) и показывать оператору кластером — так новый код предлагается на весь кластер,
  а не на отдельную реплику.
- **Отчёт по доле `OTH` и `interpretation_only`.** Регулярная строка отчёта «сколько
  фрагментов не покрыто кодбуком и сколько кодов держится на интерпретации» —
  прямой сигнал о неполноте кодбука и качестве ASR. Сейчас это только очередь ревью.
- **Хранение атрибутов без отдельной колонки.** Если в книге появится атрибут, под
  который нет колонки, можно хранить его в таблице «имя — значение» и не делать
  миграцию на каждый атрибут. В M2 такая таблица не нужна: известным атрибутам
  хватает колонок, а решение оператора — держать схему явной.

## Накопленный итог по интервью (планирование выборки)

Дашборд и отчёт M6 считают одно интервью, поэтому не отвечают на вопрос «сколько
записей ещё нужно». Нужен сводный вид по всем обработанным интервью.

- **Сводка покрытия по накопленным данным.** Те же блоки, что в дашборде, но по
  сумме интервью: аннотации по темам, использованные коды, неиспользованные коды с
  разделением «не применимо к группе» / «применимо, но не найдено». Счётчики рядом
  с числом интервью, на которых они набраны, — иначе сумма выглядит весомее, чем есть.
- **Прирост новых кодов на интервью.** Сколько кодов впервые встретилось в каждой
  следующей записи. Если прирост падает к нулю, добавление интервью перестаёт
  добавлять информацию по кодбуку — это и есть основание остановить сбор, а не
  субъективное «кажется, хватит». Слово «насыщено» не используется: показывается
  кривая прироста и её последние значения.
- **Разбивка по группам.** «ТОРГ» и «Не торгующие» сравниваются по покрытию тем и
  кодов, иначе сводка смешивает две разные структуры гайда и занижает темы, которые
  есть только у одной группы. Сравнение групп в M6 явно исключено, здесь оно
  возвращается как отдельная задача.
- **Стоимость и очередь.** Число интервью на группу, из них с расшифровкой и с
  разметкой, — чтобы видеть, где запас записей уже есть, а где нет.
- **Осторожность с выводами.** Пока интервью мало, сводка остаётся счётчиком, а не
  оценкой выборки: репрезентативность не считается, различия между группами не
  проверяются статистически.

Область не определена: сводка по всем интервью базы или по явно выбранному набору.
Требует отдельного SPEC с решением оператора по §11–§12, если понадобится хранить
снимки сводки.

## Кодбук и разметка: M3 отложен и ширина кодбука

- **M3 отложен.** Лексические векторы, `similar` и `propose-oth` в текущей
  итерации не реализуются: кластеризация пяти `OTH` не даёт устойчивого
  результата, а дашборду и отчёту векторы не нужны. Контракты M3 остаются в
  SPEC-M6 как задел; возвращаться к ним предлагается после того, как появится
  несколько интервью и станет ясно, насколько часто встречается `OTH`.
- **Двухуровневое кодирование «семья → код».** Сначала модель относит фрагмент
  к семье (Риски, Проверка, Ошибки исполнения и т. д.), затем выбирает код
  внутри семьи. Это уменьшает пространство выбора на каждом шаге: сейчас 42
  кода конкурируют одновременно, и при такой ширине и модель, и эксперт хуже
  удерживают различия между близкими кодами.
- **Сокращённый рабочий кодбук.** Отдельный набор кодов, реально
  встречающихся в разговорах с клиентами, с сохранением полного кодбука для
  расширения. Сокращать предлагается по накопленной статистике нескольких
  интервью, а не по одному: на одном интервью не отличить редкий код от
  ненужного.
- **Слияние редких кодов.** Коды, которые различаются одним оттенком смысла и
  на практике ставятся неразличимо (например, подвиды ответственности),
  объединяются в один с явной пометкой «код не различает подтипы». Слияние
  уменьшает ширину выбора без потери покрытия.
- **Проверка по выборке 10–15 ответов с подсаженными ошибками.** В выборку
  добавляются фрагменты с заранее известными дефектами (пропущенный код,
  неверный код, пропущенный `unmarked`), и проверяется, находит ли их человек
  при ручном контроле. Это измеряет качество самого контроля, а не только
  разметки: сейчас доля проверенных аннотаций известна, а доля найденных
  ошибок — нет.
- **Слепая проверка части выборки.** Часть аннотаций проверяется без показа
  решения модели: проверяющий ставит код сам, затем результаты сравниваются.
  Так видно, совпадает ли ручная проверка с моделью по существу или только
  подтверждает предложенное — сейчас `accepted` означает и то и другое.
- **Второй независимый прогон и очередь по расхождениям.** Кодирование
  повторяется вторым прогоном (другая температура или другая модель), и
  расхождения попадают в очередь ручной проверки. Это дешевле, чем проверять
  всё подряд, и показывает нестабильность разметки там, где она реальна.
