# SPEC-M2: кодирование фрагментов

Статус: approved (создан 2026-11-08; дополнен и принят 2026-11-09)
Связь с MANIFEST: разделы 2(б), 3, 4, 6.
Зависит от: SPEC-M1 (M1a, M1b, M1c).

Черновик создан раньше остальных разделов M2: оператор зафиксировал обязательное
правило, которое нельзя потерять до начала кодирования. Дополнение 2026-11-09
заполняет остальные разделы по `specs/_TEMPLATE.md`. Приёмка 2026-11-09: три
правки оператора (asr_quality по фрагменту, вызов на реплику, определение
категории в ПОРЯДКЕ) и закрытие вопроса о модели кодирования.

## Цель

Присвоить фрагментам L2 коды кодбука так, чтобы каждое решение было проверяемо
человеком по цитате, а догадка модели не выглядела как факт из интервью.

Зачем именно так: MANIFEST §6 требует воспроизводимости и прослеживаемости, а
MANIFEST §3 — описательного анализа без подмены слов респондента. Код без
проверяемой цитаты нельзя ни перепроверить, ни защитить перед заказчиком.

## Контекст и входы

Кодирование — следующий этап после M1c. Вход модели — **реплика респондента**,
а не отдельный фрагмент: в промпт идёт дословный срез L2 (`fragment.text`) всей
реплики со списком её фрагментов, каждый из которых уже привязан к вопросу
гайда.

Что получает модель на каждый вызов (зачем — в скобках):

| Вход | Источник | Зачем нужен |
|---|---|---|
| `text` — срез L2 | `fragment.text` | Только по нему ставится код и проверяется цитата (CONSTITUTION §6) |
| `question_id` и формулировка вопроса | `fragment.question_id` → `question.identifier`, `question.wording` | Задаёт тему: о чём реплика |
| `is_probe` | `utterance.is_probe` блока | Отличает основной вопрос от уточнения при разборе порядка |
| Текст предшествующих реплик интервьюера | `utterance` интервью до этой реплики (по порядку id) | Определяет признак ПОРЯДОК: прозвучала ли категория раньше |
| `prior_interviewer_turn_id` | `fragment.prior_interviewer_turn_id` | Привязка к конкретной реплике интервьюера перед ответом |
| `asr_quality` | `fragment.asr_quality` (`ok` / `doubtful` / `garbled`), считается по самому фрагменту | Решает, кодировать ли фрагмент и нужна ли ручная проверка |
| Группа респондента | `interview.group` | Атрибут ГРУППА; на выбор кода не влияет, нужен для выгрузки |

Почему не только номер вопроса: номер говорит, о чём реплика, но не о том,
прозвучала ли категория раньше. В R01 вопрос 8 напрямую не задан, блоки
00:14:02 и 00:35:45 привязаны к нему как уточнения о рисках, а перед первым
блоком интервьюер уже спрашивал про опасения. Судить о спонтанности по
`question_id` значило бы считать подсказкой ответ, привязанный к вопросу,
который в этом интервью не задавался (docs/DECISIONS.md, 2026-11-09).

Справочники берутся из рабочей книги (MANIFEST §4 — единственный
машиночитаемый источник): лист «Коды» (код, семья, название, определение,
включает, исключает, `правило_при_сомнении`) и лист «Атрибуты» (имя, тип,
описание). Жёстких списков кодов в коде нет.

## В рамках / вне рамок

В рамках M2:

1. Кодирование фрагментов кодами текущей версии кодбука, включая `OTH`.
2. Признак ПОРЯДОК («спонтанно / по подсказке») по репликам интервьюера.
3. Правило интерпретации искажений при кодировании.
4. Проверка результата кодом: цитата, существование кода, обязательные
   атрибуты, описание `OTH`.
5. Очередь ручной проверки: выборка плюс все `OTH` плюс все ненадёжные.
6. Запись прогона в `run`, кэш, лимиты, `--dry-run`.

Вне рамок M2:

- Оценка понимания (верно / частично / неверно по фактам Финама) — см.
  открытые вопросы.
- Эмбеддинги, кластеризация `OTH`, предложения новых кодов (M3).
- Агрегация по дереву тем и дашборд (M4).
- Правка рабочей книги: имена атрибутов меняет оператор.

## Контракты данных (таблицы, схемы JSON, форматы файлов)

Следующая миграция после применённых 0001–0006 — **0007** (`0007_coding_m2.sql`).
Применённые миграции не правятся (CONSTITUTION §4). Дропов нет: только
`CREATE TABLE` и `ALTER TABLE ... ADD COLUMN`, поэтому подтверждение
деструктивной операции не требуется.

Единица вызова модели — **реплика респондента**, а не фрагмент. Одна реплика
R01 даёт от 1 до 7 фрагментов (медиана 2, в среднем 2,7 на 217 фрагментах и
80 репликах), поэтому вызов «на реплику» дешевле и даёт модели соседние
фрагменты как контекст: коды в них не должны противоречить друг другу.
Проверка цитаты при этом остаётся внутри фрагмента: цитата обязана быть
срезом своего `fragment`, а не всей реплики.

### 1. `fragment_coding` — итог кодирования фрагмента в прогоне

Одна запись на пару «фрагмент × прогон». Нужна, чтобы отличить «код не
поставлен» от «фрагмент пропущен как искажённый» и от «модель не ответила»:
без неё эти три случая в отчёте неразличимы, а повторный прогон не может
решить, что перезаписывать.

| Поле | Тип | Смысл |
|---|---|---|
| `id` | INTEGER PK | |
| `fragment_id` | INTEGER NOT NULL → `fragment(id)` | |
| `run_id` | INTEGER NOT NULL → `run(id)` | |
| `status` | TEXT NOT NULL CHECK IN (`coded`, `skipped_garbled`, `unmarked`, `failed`) | `coded` — коды поставлены; `skipped_garbled` — пропуск по искажению; `unmarked` — модель не нашла значимого; `failed` — вызов не удался |
| `note` | TEXT | Причина для `unmarked`/`failed` |
| `created_at` | TIMESTAMP DEFAULT CURRENT_TIMESTAMP | |
| UNIQUE(`fragment_id`, `run_id`) | | Повторный прогон не плодит дублей |

### 2. `annotation` — код фрагмента (существующая таблица, дополняется)

Сейчас таблица пуста (0 строк), поэтому новые колонки добавляются через
`ALTER TABLE`. `annotation.confidence` остаётся неиспользованной: её смысл
(«уверенность разметчика») заменяется явным `reliability`.

| Поле | Тип | Смысл |
|---|---|---|
| `id`, `fragment_id`, `code_id`, `source`, `run_id`, `rationale`, `status` | как сейчас | |
| `quote` | TEXT NOT NULL | Дословный срез L2 |
| `quote_start`, `quote_end` | INTEGER | Позиции в `text_unit.text`, а не во фрагменте: так цитату можно проверить одним SQL-запросом |
| `coding_id` | INTEGER → `fragment_coding(id)` | Связь с итогом прогона |
| `interpretation` | TEXT | Прочтение искажённого места моделью (правило интерпретации) |
| `interpretation_only` | INTEGER NOT NULL DEFAULT 0 CHECK IN (0, 1) | 1 — смысл кода держится только на интерпретации |
| `order_kind` | TEXT CHECK IN (`spontaneous`, `prompted`) | Атрибут ПОРЯДОК |
| `scenario` | TEXT CHECK IN (`real`, `imaginary`) | Атрибут СЦЕНАРИЙ, только для вопроса 14Т-б |
| `reliability` | INTEGER CHECK BETWEEN 1 AND 3 | Атрибут НАДЁЖНОСТЬ_КОДА |
| `reliability_note` | TEXT | Краткое обоснование надёжности |
| `oth_description` | TEXT | Обязательное свободное описание для `OTH` |

Несколько кодов на фрагмент — несколько строк `annotation` с одним
`coding_id`. Атрибуты ГРУППА и ВОПРОС отдельно не хранятся: они выводятся
соединением (`interview.group`, `fragment.question_id`), дублирование
создало бы второй источник истины.

### 3. Схема JSON-ответа модели

Промпт `prompts/code_fragment.md`, схема `CODING_SCHEMA` в модуле кодирования.
Ответ описывает **всю реплику**: список фрагментов с их кодами.

```json
{
  "fragments": [
    {
      "fragment_id": 42,
      "codes": [
        {
          "code": "R5",
          "quote": "дословный срез фрагмента",
          "rationale": "почему этот код, а не соседний",
          "order": "spontaneous",
          "scenario": null,
          "reliability": 3,
          "reliability_note": "категория названа прямо"
        }
      ],
      "interpretation": "как прочитано искажённое место или null",
      "interpretation_only": false
    }
  ]
}
```

Правила схемы: `fragments` содержит все фрагменты реплики из промпта, и
`fragment_id` обязан быть среди них; `codes` может быть пустым (тогда
`unmarked`); `code` обязан существовать в текущей версии кодбука; для `OTH`
— непустой `rationale` и описание; `order` и `scenario` — `null`, если
атрибут неприменим; `reliability` — 1–3. Пропуск фрагмента в ответе
считается `failed` для этого фрагмента: модель обязана ответить по всем.

### 4. Форматы выгрузки

Выгрузка ревью (M2) — таблица с колонками: код респондента, вопрос, текст
фрагмента L2, код, цитата, ПОРЯДОК, НАДЁЖНОСТЬ_КОДА, интерпретация, признак
ненадёжности, описание `OTH`. Реальный текст живёт только под `data/`
(CONSTITUTION §5).


## Поведение и правила (включая граничные случаи)

### Кодирование

1. Коды берутся только из листов «Коды» и «Атрибуты» текущей версии кодбука.
   Зачем: CONSTITUTION §6 запрещает коды вне текущей версии.
2. Один фрагмент может получить несколько кодов. Зачем: реплика часто
   называет риск и способ проверки одновременно; один код потерял бы часть
   смысла.
3. Код `OTH` ставится, если фрагмент значим по узлам 1–2, но не подходит ни
   под один код. Свободное описание обязательно. Зачем: иначе новый смысл
   либо пропадёт, либо будет насильно втиснут в неподходящий код.
4. При сомнении между кодами решает `правило_при_сомнении` кодбука
   (`code.tiebreak_rule`); модель обязана сослаться на него в `rationale`.
   Зачем: решение должно быть воспроизводимым, а не «на усмотрение модели».
5. Фрагмент без значимого содержания получает `unmarked` и записи
   `annotation` не создаёт. Зачем: пустая аннотация выглядела бы как код.

### ПОРЯДОК («спонтанно / по подсказке»)

1. Признак определяется по репликам интервьюера в блоке фрагмента и до него,
   а не по номеру вопроса гайда. Зачем: см. пример R01, вопрос 8.
2. `prompted` — категория кода уже названа интервьюером в этом блоке или в
   предыдущих репликах; `spontaneous` — не названа. Зачем: это разные данные
   для анализа, и смешивать их нельзя.
3. Признак ставится на каждый код, а не на фрагмент: в одной реплике одна
   категория может быть подсказана, другая — нет.
4. Если контекст интервьюера обрезан лимитом, признак получает
   `reliability` не выше 2. Зачем: неполный контекст — основание для
   перепроверки, а не для уверенного решения.

**Что считается «категорией».** Категория — это **содержание конкретного
кода**, а не его семья кодов. Семья (`code.family`) группирует коды для
отчёта, но подсказкой она не является: интервьюер, назвавший тему «риски»,
не подсказывает каждый код семьи, к которой относится слово «риск».

Пример из R01: интервьюер спрашивает про риски, респондент отвечает про
риск потери данных. Код «риск» — `prompted` (интервьюер назвал именно эту
категорию). Но если в том же ответе респондент говорит, что проверяет
надёжность брокера, код «способ проверки» остаётся `spontaneous`: слово
«риски» в вопросе интервьюера эту категорию не называло. Считать иначе
значило бы записать все коды ответа про риск как подсказанные и потерять
разницу между спонтанным и наведённым ответом.

### Правило интерпретации искажений (обязательное)

1. Модель **вправе** интерпретировать искажённое место L2 (ошибка ASR, нечитаемое
   слово, оборванная фраза), чтобы понять смысл и присвоить код. Отдельного этапа
   «интерпретация» или «извлечение сущностей» нет: это правило работы внутри
   кодирования.
2. Интерпретация записывается **в отдельное видимое поле аннотации** и не подменяет
   цитату. Цитата остаётся дословным срезом L2.
3. Код **не должен держаться только на интерпретации**. Если смысл фрагмента
   восстанавливается исключительно из догадки модели, аннотация помечается как
   ненадёжная и уходит на ручную проверку, а не принимается автоматически.
4. Интерпретация не попадает в L2 и не меняет L1: слои текста остаются
   неизменяемыми (CONSTITUTION §6).

Контракт поля зафиксирован в разделе данных: `annotation.interpretation` —
текст прочтения, `annotation.interpretation_only` — признак «смысл восстановлен
моделью», миграция 0007.

### Искажения ASR (`asr_quality`)

`asr_quality` считается **по самому фрагменту**, а не переносится с единицы L2:
кодируется фрагмент, и его качество определяется его собственным текстом.
Переноса «единица → все её фрагменты» больше нет.

Правило присвоения (`fragment.asr_quality`, миграция 0007 пересчитывает
значения; расчёт живёт в `src/qa/pipeline/`):

1. `garbled` — в тексте фрагмента есть маркер `[неразборчиво]`.
2. `doubtful` — маркера нет, но в тексте фрагмента есть хотя бы одно из:
   слово, заменённое правилом `asr_fix` этой единицы (`text_unit.changes`);
   слово из `new_term` этого интервью; подозрительное слово по лексикону
   (`normalize_rules.suspect_words`). Сравнение — по токенам в нижнем регистре.
3. `ok` — ни одного из условий выше.

Для сверки с M1b остаётся счёт по единицам L2: в R01 v8 — 190 единиц =
148 `ok` + 39 `doubtful` + 3 `garbled`. Это другая единица счёта, и смешивать
её со счётом по фрагментам нельзя.

Поведение при кодировании:

1. `garbled` — фрагмент не кодируется, получает `skipped_garbled` и
   считается пропуском; в отчёте идёт отдельной строкой, а не как «код не
   найден». Зачем: иначе пропуск по качеству текста выглядел бы как
   содержательный вывод об отсутствии категории.
2. `doubtful` — код ставится, прочтение искажённого слова пишется в
   `interpretation`. Если интерпретация непустая, `reliability` не выше 2.
   Зачем: искажение обычного слова не лишает реплику смысла, но должно быть
   видно проверяющему и не может считаться полностью надёжным кодом.
3. `ok` — обычное кодирование, `reliability` 1–3 без ограничения.

### Признак «код держится только на интерпретации»

Признак ставится **только флагом модели**: `interpretation_only = true`.
Дополнительной проверки долей символов нет: порог доли интерпретированных
слов не вводится, потому что модель уже видит, на чём построен код, а
порог пришлось бы калибровать без золотого набора. Зачем всё равно хранить
флаг: он отделяет догадку от чтения по тексту и включает обязательную
ручную проверку.

Следствия флага и качества текста:

| Условие | `reliability` | Ручная проверка |
|---|---|---|
| `interpretation_only = true` | не выше 1 | обязательно |
| `asr_quality = doubtful` и `interpretation` непустая | не выше 2 | обязательно |
| `asr_quality = ok`, флага нет | 1–3 | только по выборке |
| `asr_quality = garbled` | не ставится | фрагмент не кодируется |

### Проверка результата кодом

Перед записью каждая аннотация проверяется (зачем — в скобках):

1. Цитата равна срезу L2: `text_unit.text[quote_start:quote_end] == quote`, и
   срез лежит внутри `fragment`. (CONSTITUTION §6: цитата, которой нет в
   тексте, делает аннотацию недействительной.)
2. Код существует в текущей версии кодбука. (Иначе код нельзя сопоставить с
   темой и посчитать.)
3. Обязательные атрибуты заполнены по листу «Атрибуты»; неприменимый
   атрибут — `NULL`, а не пустая строка. (Пропуск и «неприменимо» — разные
   данные.)
4. У `OTH` есть непустое описание. (CONSTITUTION §6.) Проверка живёт в коде
   записи аннотаций, триггера в БД нет: правило одно, и его достаточно
   проверять в одном месте; триггер дублировал бы логику и усложнял миграцию.
5. `reliability` в диапазоне 1–3. (Шкала задана в книге.)

Нарушение любой проверки — отказ аннотации с причиной в `fragment_coding.note`,
а не молчаливая запись.

### Персональные данные (`pii_flag`)

Правило единое для M1b и M2: `pii_flag` — **метка для ручной проверки, а не
блокировка**. Отправка в модель не останавливается, потому что шаблон
срабатывает и на денежных суммах («100 000 рублей»), и на номерах договоров:
блокировка выбросила бы из кодирования содержательные ответы. Настоящие
имена уже заменены кодами при загрузке (CONSTITUTION §5), а телефон, e-mail
и номер счёта в ответе о рисках не меняют смысл кода.

Что делается вместо блокировки:

1. Фрагмент с `pii_flag` кодируется как обычно.
2. Он попадает в очередь ручной проверки вместе с ненадёжными. Зачем: это
   место, где возможна настоящая утечка, и её должен увидеть человек.
3. В логах и отчётах по-прежнему нет текста реплик (CONSTITUTION §5) — это
   не меняется ни при каком значении флага.

Так снимается расхождение с SPEC-M1: там `pii_flag` уже описан как метка,
не блокирующая отправку; здесь зафиксировано то же правило и добавлено
следствие для очереди ревью.

### Ручная проверка

Очередь = выборочная доля `m2.review_sample_share` (стартовое значение 0,1)
+ **все** аннотации с `OTH` + **все** аннотации с `interpretation_only = 1`
или `reliability = 1` + все аннотации фрагментов `doubtful` с непустой
интерпретацией + все аннотации фрагментов с `pii_flag`. Зачем: `OTH` — место,
где кодбук не покрывает смысл, ненадёжные — место, где решение может быть
догадкой, `pii_flag` — место возможной утечки; ни один из этих случаев нельзя
проверять выборочно. Золотого набора и ручной разметки всех фрагментов нет,
поэтому выборка обязательна, а не «по желанию».

Решения пишутся в существующую `review` (`approved` / `rejected` /
`needs_revision`), статус аннотации меняется на `accepted` / `edited` /
`rejected`. Зачем: CONSTITUTION §6 — повторный прогон не перезаписывает
принятое и исправленное.

### Прогон, кэш, лимиты

1. **Один вызов модели на реплику респондента.** В промпт идёт реплика L2
   целиком со списком её фрагментов (`fragment_id`, текст, вопрос,
   `asr_quality`), модель возвращает коды по каждому фрагменту. Зачем: вызов
   «на фрагмент» множит стоимость (217 фрагментов против 80 реплик в R01) и
   теряет соседний контекст, из-за чего соседние фрагменты одной мысли
   получают противоречащие коды. Проверка цитаты остаётся внутри фрагмента:
   цитата — срез своего `fragment`, а не всей реплики.
2. LLM только через `llm/`; ответ — JSON по схеме; температура 0 для
   кодирования; кэш по ключу «хеш промпта + хеш входа + модель»
   (CONSTITUTION §7).
3. Лимит вызовов и бюджет — из `config.yaml` (`llm.max_calls_per_run`,
   секция `m2`). Зачем: прогон на 80 репликах R01 не должен упираться в
   неожиданный счёт.
4. `--dry-run` показывает число реплик к кодированию, число фрагментов и
   оценку вызовов без сети.
5. Каждый прогон пишется в `run`: модель, хеш промпта, версия кодбука,
   версия кода. Зачем: MANIFEST §6 — воспроизводимость.
6. Ошибка валидации ответа по реплике повторяется по общему правилу `llm/`
   (2 попытки); после этого все фрагменты реплики получают `failed` с
   причиной. Зачем: частично записанная реплика дала бы ложное ощущение
   полноты.

### Граничные случаи

| Случай | Поведение |
|---|---|
| `asr_quality = garbled` | `skipped_garbled`, кодов нет, отдельная строка отчёта |
| Фрагмент вне гайда (`question_id IS NULL`) | Кодируется; ВОПРОС пуст, ПОРЯДОК = `spontaneous`, если интервьюер категорию не называл |
| Модель вернула пустой `codes` у фрагмента | `unmarked` с причиной |
| Модель пропустила фрагмент в ответе | `failed` для этого фрагмента |
| Модель вернула код вне кодбука | Аннотация отклонена, `failed`, причина в `note` |
| Цитата не найдена в L2 | Аннотация отклонена, `failed` |
| `OTH` без описания | Аннотация отклонена проверкой кодом |
| Повторный прогон | Обновляет только `proposed`; `accepted`/`edited` не трогает |
| Сбой вызова LLM | `failed` для всех фрагментов реплики, 2 попытки, затем запись |

## Критерии приёмки (проверяемые, с командами)

1. **Цитаты дословны.** Ни одной аннотации с цитатой, не равной срезу L2:
   ```sql
   SELECT a.id FROM annotation a
   JOIN fragment f ON a.fragment_id = f.id
   JOIN text_unit t ON f.text_unit_id = t.id
   WHERE substr(t.text, a.quote_start + 1, a.quote_end - a.quote_start) <> a.quote;
   ```
   Запрос возвращает 0 строк; в тестах то же проверяется на синтетике.
2. **Коды существуют.** `annotation.code_id` всегда ссылается на код текущей
   версии кодбука; неизвестный код отклоняется.
3. **`OTH` с описанием.** Аннотация `OTH` без `oth_description` не
   записывается; тест проверяет отказ и причину в `fragment_coding.note`.
4. **Искажения.** Фрагмент с `asr_quality = garbled` не имеет аннотаций и
   учтён как `skipped_garbled`; отчёт печатает отдельную строку с числом
   пропусков и числом `doubtful` на ручной проверке.
5. **Ненадёжность.** Аннотация с `interpretation_only = 1` или
   `reliability = 1` попадает в очередь ручной проверки целиком, а не
   выборочно.
6. **ПОРЯДОК по репликам, а не по номеру вопроса.** Тест на синтетике,
   повторяющий случай R01: вопрос гайда в интервью не задан, категория
   названа интервьюером раньше → `prompted`.
7. **Один вызов на реплику.** Тест на синтетике: реплика из трёх фрагментов
   даёт один вызов модели, три записи `fragment_coding` и цитаты внутри
   своих фрагментов.
8. **LLM через `llm/`, сеть не нужна.** Тесты с заглушкой; провайдер
   подменяется, прямых SDK-вызовов нет.
9. **Воспроизводимость.** Одинаковые вход и параметры дают те же аннотации;
   кэш используется; `run` записан.
10. **Проверки проекта.** `uv run pytest -q`, `uv run ruff check .`,
    `uv run ruff format --check .`, `uv run mypy src` — без ошибок.

## Пилот на R01

Отдельный пункт приёмки: пилот — не тест, а замер на реальном интервью
после «принято». Без него неизвестны ни стоимость ручной проверки, ни
качество кодов.

1. Прогнать M2 на R01 (80 реплик, 217 фрагментов; по фрагментам 0 `garbled`
   и 104 `doubtful`).
2. Вывести отчёт: число вызовов, `coded` / `unmarked` / `failed` /
   `skipped_garbled`, число аннотаций, доля `OTH`, число `doubtful` и
   `interpretation_only`.
3. Провести ручную проверку очереди и посчитать **долю аннотаций, принятых
   без правок**: `принято / (принято + исправлено + отклонено)`. Порог не
   задаётся: метрика нужна как базовое значение для следующих прогонов и
   для решения о доле выборки.
4. Зафиксировать время проверки на аннотацию. Зачем: без этого нельзя
   оценить стоимость полного корпуса.

Метрика «доля принятых без правок» — основной результат пилота; порог
появится только после второго интервью, когда будет с чем сравнивать.


## Тесты

- `tests/test_coding.py` — юнит-тесты: сборка промпта на реплику (вход и
  отсутствие лишних данных), валидация схемы ответа по фрагментам, проверка
  цитаты внутри фрагмента, проверка существования кода, обязательное
  описание `OTH`, диапазон `reliability`.
- `tests/test_coding_order.py` — признак ПОРЯДОК: подсказка в блоке,
  подсказка в предыдущей реплике, спонтанность, обрезанный контекст.
- `tests/test_coding_distortion.py` — `garbled` → пропуск и строка отчёта;
  `doubtful` с непустой интерпретацией → `reliability` не выше 2;
  `interpretation_only` → `reliability` не выше 1 и обязательная проверка.
- `tests/test_coding_review.py` — состав очереди: выборка + все `OTH` + все
  ненадёжные; повторный прогон не трогает `accepted`/`edited`.
- Сквозной тест на синтетическом интервью: M1a → M1b → M1c → M2, заглушка
  LLM, один вызов на реплику, проверка записи `run` и аннотаций.

## Риски и зависимости

- **Модель придумывает код или цитату.** Снижение: проверка по L2 и кодбуку,
  отказ вместо записи, тесты на подделку.
- **Слишком много `OTH`.** Снижение: отдельная очередь ревью и отчёт по
  числу `OTH`; кластеризация — M3.
- **Искажения ASR в R01 заметны.** Считая по фрагментам (их и кодируем), из
  217 фрагментов **0 `garbled`, 104 `doubtful` (47,9 %), 113 `ok` (52,1 %)**.
  `garbled` по фрагментам = 0, потому что маркера `[неразборчиво]` в
  актуальной L2 v8 и во фрагментах нет — он остался только в версиях 1–3.
  Причины `doubtful` пересекаются: `asr_fix` — 15 фрагментов, `new_term` — 55,
  подозрительное слово — 84; у 48 фрагментов сработало больше одной причины.
  Считая по единицам L2 v8 (для сверки с M1b): из 190 единиц 3 `garbled` и
  39 `doubtful`. Раньше в этом разделе стояли 15/132 по фрагментам (это был
  перенос качества единицы на все её фрагменты) и 30/317 (суммы по всем
  восьми версиям L2). Снижение: пропуск `garbled`, ручная проверка `doubtful`
  с интерпретацией; стоимость оценивается на пилоте.
- **Длинный контекст интервью.** Снижение: ограничение лимита реплик
  интервьюера и понижение `reliability` при обрезке.
- **Новых зависимостей нет.** Нужны только существующие `llm/`, `db/`,
  `pydantic`.
- Зависимость от M1c: без `fragment` и `prior_interviewer_turn_id` этап
  невозможен.

## Проверка по конституции (что из CONSTITUTION здесь критично)

- §4: миграция 0007, применённые не правятся, SQL только в `db/`.
- §5: реальные тексты не в репозитории, нет текста реплик в логах.
  `pii_flag` — **метка для ручной проверки, а не блокировка**: правило
  единое для M1b и M2 (см. «Поведение и правила», PII).
- §6: коды только из текущей версии, цитата проверяется по L2, `OTH` с
  описанием, повторный прогон не перезаписывает принятое, слои неизменяемы.
- §7: LLM только через `llm/`, JSON по схеме, температура 0, кэш, лимиты,
  промпты в `prompts/`, заглушка в тестах.
- §9: юнит-тесты и один сквозной на синтетике; готово только при зелёных
  `pytest`, `ruff` и типах.

## Открытые вопросы

1. **Имя атрибута уверенности разметчика.** В листе «Атрибуты» поле
   `УВЕРЕННОСТЬ` описано как «уверенность разметчика (модели или человека),
   1–3», но «уверенность» уже занята неуверенностью респондента (маркеры
   L2). **Решено:** `НАДЁЖНОСТЬ_КОДА` (1–3, «насколько код следует из
   текста»), колонка `annotation.reliability`. Книгу правит оператор.
2. **Поле интерпретации: имя и форма хранения.** **Решено:** колонки
   `annotation.interpretation` (TEXT) и `annotation.interpretation_only`
   (0/1), а не отдельная таблица: интерпретация относится к цитате этой
   аннотации, а колонка видна в выгрузке без соединения.
3. **Формальное определение «код держится только на интерпретации».**
   **Решено:** только флаг модели `interpretation_only`; порог доли
   интерпретированных символов не вводится, потому что калибровать его
   не на чем (золотого набора нет), а модель видит основание кода.
4. **Оценка понимания (верно / частично / неверно по фактам Финама).**
   **Решено: вариант A — в M2 не делать.** Причина: эталон Финама и ручная
   сверка не готовы, а оценка факта смешалась бы с кодом. Вернуться
   отдельным SPEC, когда эталон появится.
5. **Доля ручной выборки** `m2.review_sample_share` (стартово 0,1) —
   уточняется после пилота по времени проверки.
6. **Модель для кодирования.** **Решено:** кодирование идёт на общей модели
   `llm.model` (`LLM_MODEL` из `.env`) — там стоит сильная модель. Отдельный
   ключ `llm.model_coding` не вводится: одна настройка на этап, без ветвления
   по задачам. Нормализация остаётся на `LLM_MODEL_NORMALIZE` и не меняется.
