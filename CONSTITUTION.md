# CONSTITUTION: правила работы над проектом

Применяются к каждой задаче. Приоритет: прямая инструкция оператора в текущей задаче, затем MANIFEST, затем CONSTITUTION, затем PLAN, затем SPEC. Правила безопасности (разделы 3 и 5) не ослабляются ничем, кроме явного решения оператора.

## 1. Порядок работы
1. Работа идёт по цепочке MANIFEST, PLAN, SPEC, tasks, реализация. Код без спецификации не пишется (кроме правки опечаток и документации).
2. Перед реализацией агент читает MANIFEST, CONSTITUTION и нужный SPEC, затем пишет краткий план задач и ждёт подтверждения, если задач больше трёх или затрагивается схема БД.
3. Перед новым кодом агент ищет существующий. Дублирование функциональности запрещено.
4. Не делать то, чего нет в спецификации (без «заодно»). Идеи записываются в `docs/IDEAS.md`.

## 2. Окружение и зависимости
- Менеджер: только `uv`. Команды: `uv sync`, `uv run ...`, `uv add ...`. Никаких `pip install`, `python -m venv` вручную и установок в глобальный Python.
- Виртуальное окружение: `.venv` в корне проекта, не коммитится. Версия Python зафиксирована в `.python-version`, `pyproject.toml` и `uv.lock` коммитятся.
- Новая зависимость допускается только с обоснованием в SPEC (зачем, чем заменить нельзя, размер и лицензия). Предпочтение стандартной библиотеке.
- Зависимости разработки (ruff, pytest, type checker) в отдельной группе.
- Пути только через `pathlib`. Кодировка UTF-8 везде явно (`encoding="utf-8"`). Тексты на русском должны проходить сквозь пайплайн без искажений.

## 3. Конфигурация и секреты
- Все настройки (эндпоинты, модели, пути, лимиты) в `config.yaml` (без секретов) и переменных окружения (секреты). Загрузка через единый модуль настроек с валидацией.
- Файл `.env` не коммитится. В репозитории лежит `.env.example` с именами переменных без значений.
- Секреты, ключи и эндпоинты не попадают в код, логи, БД, тесты, сообщения коммитов и отчёты агента.
- Если секрет оказался в файле или истории, агент останавливается и сообщает оператору.

## 4. База данных (SQLite)
- Схема меняется только через пронумерованные миграции в `migrations/` (`0001_*.sql`). Применённая миграция не редактируется; исправление идёт новой миграцией.
- При подключении: `PRAGMA foreign_keys=ON`, `journal_mode=WAL`. Запросы только параметризованные.
- Файл БД лежит в `data/` и не коммитится. Перед миграцией автоматически делается копия.
- Деструктивные операции (DROP, DELETE без условий, массовый UPDATE) требуют явного подтверждения оператора.
- Сырые данные (транскрипты, исходный кодбук) неизменяемы. Производные таблицы можно пересобрать из сырых данных одной командой.
- Работа с БД идёт через слой репозиториев (`db/`). SQL в модулях пайплайна и дашборда не разбросан.
- Стадии пайплайна идемпотентны: повторный запуск не создаёт дублей и не стирает ручные правки.

## 5. Данные и приватность
- Реальные транскрипты и производные данные не коммитятся (`data/` в `.gitignore`). Для тестов только синтетические фикстуры.
- Имена респондентов заменяются кодами при загрузке (стадия 0). Таблица соответствия хранится вне репозитория и БД.
- В логах нет текста реплик; допустимы идентификаторы, длины и хеши.
- Перед отправкой текста во внешнюю модель срабатывает фильтр шаблонов (телефоны, e-mail, номера счетов). Совпавшие фрагменты уходят на ручную проверку.

## 6. Методологические правила (предметная область)
- Коды берутся только из текущей версии кодбука. Новые коды создаются через код `OTH` с описанием.
- Индуктивные расширения кодбука принимает только оператор; базовый кодбук (приложение Б) неизменяем; расширения живут в `schema/codebook_extensions.yaml` и в БД.
- Каждая аннотация имеет дословную цитату с позицией в тексте. Цитата, которой нет в тексте, делает аннотацию недействительной.
- Модель предлагает, человек решает. Повторный прогон не перезаписывает аннотации со статусом «принято» или «исправлено».
- Каждый прогон записывается в `run`: модель, хеш промпта, версия кодбука, версия кода, дата.
- Показатели насыщения помечаются как эвристика. Сравнения групп только описательные.
- Слои текста L0, L1, L2. Анализ, цитаты в отчёте и поиск идут по L2. L0 и L1 не изменяются и не публикуются. Нормализация не добавляет сведений, не удаляет маркеры неуверенности и не раскрывает местоимения. Дословность цитаты проверяется относительно L2 и имеет ссылку на L1.
- В отчёте указывается тип расшифровки: машинная расшифровка с лёгкой редакцией. Вырезки отмечаются многоточием, добавления для ясности в квадратных скобках.
- Текст отчёта пишет модель только по готовым числам и цитатам из БД. Числа в тексте проверяются автоматически на совпадение с БД.

## 7. Вызовы LLM
- Только через модуль `llm/` (методы вида `complete_json(prompt, schema)` и `embed(texts)`). Прямые вызовы SDK из других модулей запрещены.
- Ответ только в виде JSON по схеме с валидацией. При ошибке валидации ограниченное число повторов (по умолчанию 2), затем запись как «не размечено».
- Для кодирования температура 0. Кэш по ключу (хеш промпта, хеш входа, модель).
- Лимит вызовов и бюджет на прогон задаётся в конфигурации. Режим `--dry-run` показывает объём работы без вызовов.
- Промпты хранятся в файлах `prompts/` и версионируются. В тестах LLM заменён заглушкой, сеть не используется.

## 8. Качество кода
- Типизация, форматирование и линт: `ruff` (format и check), проверка типов выбранным инструментом. Всё проходит без предупреждений перед завершением задачи.
- Функции небольшие и по возможности чистые. Ввод-вывод вынесен на границы.
- Логи через `logging` с идентификатором прогона. Никаких `print` в библиотечном коде.
- Исключения не глушатся широким `except`. Ошибки данных превращаются в явные статусы, а не в молчаливый пропуск.
- Комментарии объясняют «почему», а не «что».

## 9. Тесты и приёмка
- Каждая стадия пайплайна имеет юнит-тесты и один сквозной тест на синтетическом интервью.
- Задача считается выполненной только если: критерии приёмки из SPEC выполнены, `uv run pytest`, `ruff` и проверка типов проходят, документация обновлена.
- Запрещено ради зелёных тестов: удалять тесты, ослаблять проверки, вшивать ожидаемые значения, ловить исключения целиком.

## 10. Git
- Ветка на задачу (`spec-XX/краткое-имя`). Небольшие коммиты с осмысленными сообщениями.
- Не коммитить: `data/`, `.env`, `.venv`, файлы кэша, БД.
- `pre-commit`: ruff, проверка секретов, проверка размера файлов.
- Нет `force push` и переписывания истории без команды оператора.

## 11. Выход из «паразитного цикла»
Агент останавливается и задаёт вопрос оператору, если:
- одна и та же ошибка или тест не проходят после трёх попыток с разными подходами;
- два разных подхода к задаче провалились;
- задача требует изменения вне границ SPEC (новая зависимость, схема БД, архитектура, интерфейс);
- спецификация неоднозначна или противоречит MANIFEST;
- потребовалось затронуть больше файлов или строк, чем ожидалось в SPEC, более чем в два раза;
- агент ловит себя на том, что откатывает и повторяет собственные изменения.

Формат остановки (см. `WORKFLOW.md`, шаблон STUCK): что пытался, что получилось, гипотеза причины, варианты решения, конкретный вопрос. Обход проблемы через ослабление тестов, глушение ошибок или заглушки запрещён.

## 12. Границы, где нужно разрешение оператора
- Файлы `MANIFEST.md`, `CONSTITUTION.md`, исходный кодбук (приложение Б).
- Удаление данных, применённых миграций, веток.
- Добавление зависимостей, изменение схемы БД, смена провайдера LLM.
- Любые сетевые вызовы, кроме настроенных эндпоинтов LLM.

## 13. Отчёт по завершении задачи
Коротко: что сделано, чем проверено (команды и итог), что отличается от SPEC и почему, открытые вопросы. Решения, влияющие на архитектуру, записываются в `docs/DECISIONS.md` (дата, решение, причина, альтернативы).
