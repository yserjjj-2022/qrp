# SPEC-M6: сквозной проход R01 до артефакта (M4 → M5 → M3)

Статус: approved (создан 2026-11-10; правки оператора и условия approve
выполнены 2026-11-10)
Связь с MANIFEST: разделы 2(б), 2(в), 3, 5, 6, 8.
Зависит от: SPEC-M1 (M1a, M1b, M1c), SPEC-M2.

Отступление от PLAN: PLAN требует отдельный SPEC на каждый этап, здесь M3, M4
и M5 объединены в один SPEC, потому что цель итерации — не приёмка этапов по
отдельности, а один сквозной артефакт на R01. Причина и альтернатива
зафиксированы в `docs/DECISIONS.md` (2026-11-10). Порядок реализации внутри
SPEC: M4, затем M5, затем M3: дашборду и отчёту эмбеддинги не нужны, а
кластеризация пяти записей `OTH` даёт мало.

## Цель

Довести R01 от размеченных фрагментов до двух HTML-артефактов: дашборда
покрытия дерева тем и итогового отчёта, собранного только по числам и цитатам
из БД. Промежуточная цель — увидеть, где дыры в покрытии кодбука, прежде чем
дорабатывать промпт кодирования.

Зачем именно так: MANIFEST §8 требует, чтобы первый транскрипт проходил весь
путь до дашборда и отчёта, а отчёт не содержал чисел, которых нет в базе.
Сейчас `src/qa/report/` и `src/qa/dashboard/` пусты, агрегации по дереву нет,
поэтому без этого SPEC нельзя ни оценить покрытие, ни показать результат.

### 5. Лексические векторы (M3)

Контракт `embedding` не меняется, миграция не нужна. В таблице
`embedding.fragment_id` объявлен `UNIQUE`, поэтому **ключ записи —
`fragment_id`**: одна строка на фрагмент, `model` — атрибут строки, а не часть
ключа.

| Поле | Значение |
|---|---|
| `fragment_id` | фрагмент интервью (уникальный ключ строки) |
| `model` | `lexical-tfidf-v1:<hash>` — версия правила; перезаписывается вместе с вектором |
| `vector` | JSON `{"dim": N, "idx": [i, ...], "val": [w, ...]}` — разреженный вектор, индексы по возрастанию |

`<hash>` считается sha256 (первые 12 символов hex) от канонического JSON
следующих величин, чтобы любое изменение весов меняло версию:

1. отсортированный список лемм словаря;
2. `N` — число фрагментов корпуса (от него зависит IDF);
3. частоты документов: `[[лемма, df], ...]` по возрастанию леммы;
4. версия `pymorphy3` (`pymorphy3.__version__`) и версия правила
   (`lexical-tfidf-v1`).

Зачем все четыре: при добавлении интервью список лемм может не измениться, но
`N` и `df` изменятся, а значит изменятся веса IDF и сами векторы. Хеш только по
леммам оставил бы старые векторы «актуальными» при других весах.

Словарь строится по всем фрагментам интервью: токены → леммы `pymorphy3`,
отбрасываются токены короче 2 символов и не-кириллические/не-латинские.
Вес — `tf * idf` с `idf = ln((1 + N) / (1 + df)) + 1`, затем L2-норма.
Словарь не сохраняется отдельно: он восстанавливается из текста фрагментов,
а `<hash>` позволяет отличить другую версию правила и другие веса.

Сходство — косинус по разреженным векторам; при нулевой норме сходство 0.

## Поведение и правила (включая граничные случаи)

### M4. Агрегация покрытия

1. В агрегаты идут только аннотации в статусе `accepted` и `edited`. `proposed`
   не учитываются и выводятся отдельным числом «не учтено» (в отчёте — 66 на
   снимке). Зачем: CONSTITUTION §6 — решение человека важнее разметки модели.
2. Аннотация относится к теме через `code_id → theme_code`. Код без темы
   считается не покрытым и попадает в список неиспользованных с семьёй.
3. Статус листа по числу принятых аннотаций темы. Названия описывают только
   наличие материала: на одном интервью число аннотаций не показывает, что
   тема раскрыта. Границы берутся из `config.yaml`:
   - `annotations < m4.theme_low_min_annotations` (0) → `no_data`
     («нет данных»);
   - `theme_low_min_annotations <= annotations < theme_high_min_annotations`
     (1–3) → `few` («мало»);
   - `annotations >= theme_high_min_annotations` (4 и больше) → `has_data`
     («есть данные»).
   Порог не подбирается под красивую градацию: шкала отвечает только на
   вопрос «есть ли чем показать тему». В интерфейсе статус всегда подписан
   «эвристика, 1 интервью» (CONSTITUTION §6).
4. `covered_fragments` — число различных фрагментов с хотя бы одной принятой
   аннотацией по кодам этой темы; дополнительно выводится процент от всех
   фрагментов интервью (217 на снимке).
5. **Применимость кода к группе интервью.** Признак `applicable` у
   неиспользованного кода определяется по вопросам гайда, связанным с кодом
   через `question_code`, и группе интервью:
   - берутся все вопросы кода в текущей версии кодбука;
   - код применим, если хотя бы один его вопрос имеет группу, равную
     `groups.universal` или канонической группе интервью после нормализации
     (п. 6; для R01 — «Все» или «Не торгующие»);
   - код, у которого все вопросы относятся только к чужой группе (для R01 —
     «ТОРГ»), считается неприменимым к группе интервью;
   - код без вопросов (индуктивный `OTH`) считается применимым.
   Неиспользованные коды идут одним списком с разной пометкой:
   «не применимо к группе» (для R01 — все 8 E-кодов: их вопросы 9Т, 14Т-а,
   14Т-б относятся к «ТОРГ») и «применимо, но не найдено» (18 кодов: A 7,
   N 4, B 2, V 2, R 2, C 1). Второе — сигнал о покрытии, первое — не дефект.
6. **Сравнение групп — по каноническому значению, без учёта регистра.**
   Группы в книге и в БД пишутся по-разному: `interview.group` приходит из
   листа «Интервью» и уже нормализован при загрузке, `question.group` — из
   листа гайда. Регистр, лишние пробелы и подчёркивания не должны влиять на
   применимость. Правило одно и то же в агрегации, применимости кодов и списке
   вопросов без ответа:
   - обе группы приводятся к канонической форме существующей функцией
     `qa.settings.normalize_group` (алиасы и `canonical` — из секции `groups`
     `config.yaml`, ключ сравнения — `strip` + `casefold` + схлопывание
     пробелов и подчёркиваний). Набор алиас не расширяется в этой итерации:
     используется то, что уже задано оператором в конфиге;
   - сравнение идёт по каноническим строкам, а не по сырым значениям из БД;
   - группа-маркер «вопрос задаётся всем» берётся из `groups.universal`, в коде
     не зашита;
   - если группа не распознана, она сравнивается как есть после `strip` —
     это лучше, чем считать её чужой молча.
   Отдельно: если `interview.group` в БД записан строчными («не торгующие»),
   нормализация при чтении всё равно даёт каноническое «Не торгующие» и
   применимость не ломается.
7. `covered_fragments` — число различных фрагментов с хотя бы одной принятой
   аннотацией по кодам этой темы; дополнительно выводится процент от всех
   фрагментов интервью (217 на снимке).
8. **Доля принятых аннотаций на `doubtful`.** Дополнительно считается
   качество материала: сколько принятых аннотаций опирается на фрагменты с
   `asr_quality = 'doubtful'` (39 из 48 на снимке) и на скольких `doubtful`
   фрагментах есть принятая аннотация (33 из 106). Показатель выводится в
   блоке качества данных дашборда и в блоке чисел отчёта: он говорит, какая
   часть выводов держится на распознанном с сомнением тексте.
9. `cumulative` — по принятым аннотациям темы, упорядоченным по `utterance.id`,
   затем `fragment.start`: на каждом шаге число различных кодов, встреченных
   до этого шага включительно. Кривая рисуется как инлайновый SVG без
   JavaScript.
10. Цитаты для дашборда: до `m4.quotes_per_theme` штук на тему, только из
    принятых аннотаций, по тексту L2 версии прогона. Если цитата длиннее
    `m4.quote_max_chars`, берётся префикс по границе слова и добавляется ` …`
    (вырезка отмечена многоточием, CONSTITUTION §6).
11. Узел агрегирует темы: суммы аннотаций и различных кодов; собственных
    аннотаций у узла нет.
12. Вопросы без ответа считаются только по вопросам, применимым к группе
    интервью: каноническая группа вопроса равна `groups.universal` или
    канонической группе интервью (п. 6). Вопросы чужой группы в этот список не
    попадают.
13. Интервью без принятых аннотаций — не ошибка: дашборд строится, все листья
    `no_data`, число принятых 0.

### M5. Отчёт

1. Отчёт собирается из модели `InterviewReport`; рендер не считает чисел.
2. Обязательные блоки и порядок: происхождение → числа → дерево с кривыми →
   цитаты по темам → ограничения.
3. Блок происхождения: код интервью, группа, тип расшифровки «машинная
   расшифровка с лёгкой редакцией» (CONSTITUTION §6), версия L2, версия
   кодбука, список прогонов с моделью, хешем промпта и версией кода. Здесь же
   дата снимка и `run_id`, по которому считались числа.
4. Блок чисел: дата и `run_id` снимка, статусы аннотаций,
   `coded`/`unmarked`/`skipped_garbled`/`failed`, `OTH`,
   `interpretation_only`, распределение `reliability`, доля принятых аннотаций
   на `doubtful`, покрытие кодов `N из 42` с пометкой неиспользованных
   неприменимых рядом с применимыми-но-не-найденными, покрытие фрагментов,
   вопросы без ответа. У статусов тем и у покрытия кодбука стоит та же подпись
   «эвристика, 1 интервью», что в дашборде.
5. Отдельной строкой: «`proposed` не учтено: N».
6. Блок ограничений обязателен и содержит:
   - снимок чисел привязан к дате и прогону: «числа на 2026-11-10, `run` 15»;
   - `skipped_garbled` = 0 на снимке (правило M2: искажённый фрагмент не
     кодируется и не считается «код не найден»);
   - `interpretation_only` = 1: код держится на прочтении модели, требует
     ручной проверки;
   - `doubtful` = 106, из них часть с непустой интерпретацией имеет
     `reliability` не выше 2 по правилу M2 (потолок надёжности);
   - доля принятых аннотаций на `doubtful`: 39 из 48 принятых, 33 из 106
     `doubtful`-фрагментов — показатель качества материала;
   - `unmarked` = 116 из 217 фрагментов;
   - `OTH`: «5 OTH, кластеризация предварительная», и отдельно — «порог
     кластеризации не калиброван»: `0.35` выбран как стартовое значение, на
     пяти записях калибровать нечем. Рядом с кластерами выводятся значения
     сходства, чтобы видеть плотность. Результат M3 не подаётся как вывод о
     темах;
   - использовано 16 из 42 кодов кодбука; из 26 неиспользованных «не
     применимо к группе» — 8 E-кодов, «применимо, но не найдено» — 18
     (A 7, N 4, B 2, V 2, R 2, C 1). Первое не дефект, второе — сигнал
     о покрытии;
   - одно интервью, группа «Не торгующие»: темы «Ошибки исполнения» и
     «Предупреждения» пусты, вопросы 9Т, 14Т, 19Т не применимы — это не
     дефект кодирования;
   - `reference_fact` пуст, поэтому оценка понимания не делается;
   - статусы листьев — эвристика на одном интервью;
   - **66 `proposed` не учтены**: числа покрытия и качества изменятся после
     дальнейшего ревью аннотаций.
7. Цитаты: только из принятых аннотаций, только по L2 версии прогона, с
   многоточием при вырезке. Цитат вне текста быть не может: позиции берутся
   из `annotation.quote_start/quote_end` и проверяются при сборке.
8. Нарратив модели в этой итерации **не пишется**. Отчёт на детерминированном
   шаблоне: текст ограничений и подписи блоков фиксированы. CONSTITUTION §6
   предполагает текст модели с проверкой чисел; шаблон заменяет нарратив на
   эту итерацию, флаг `--narrative` отложен до отдельного SPEC. Причина:
   проверка чисел надёжна для прямых чисел и слаба для производных
   формулировок, а отчёт без нарратива не может соврать.
9. Отчёт без принятых аннотаций собирается с пустым деревом и явной строкой
   «принятых аннотаций нет».

### M3. Векторы, похожие, предложения по OTH

1. `build-vectors <interview>` считает векторы по фрагментам интервью и пишет
   `embedding`. Команда **идемпотентна** (CONSTITUTION §4: повторный запуск не
   создаёт дублей и не стирает ручные правки). Ключ записи один —
   **`fragment_id`** (в схеме он `UNIQUE`), `model` — атрибут строки:
   - если `<hash>` совпадает с `embedding.model` существующей строки, вектор
     **не пересоздаётся**: строка остаётся как есть, фрагмент пропускается;
   - если строки нет или `<hash>` в ней другой, выполняется upsert по
     `fragment_id`: строка обновляется (вектор и `model`), дубль не создаётся;
   - повторный запуск с тем же текстом и той же версией правила даёт тот же
     `<hash>` и те же значения — результат детерминирован.
   Вывод команды печатает, сколько векторов создано, обновлено и пропущено.
2. Если `<hash>` отличается от записанного в `embedding.model`, векторы
   пересчитываются: старое правило больше не действительно, потому что изменился
   словарь, `N`, `df` или версия `pymorphy3`. Строки заменяются тем же upsert по
   `fragment_id`, а не накапливаются.
3. `similar <interview> --fragment <id> --top-k N` печатает id фрагментов и
   оценки косинуса, без текста реплик в логах.
4. `propose-oth <interview>` группирует фрагменты с `OTH`-аннотациями в статусе
   `accepted`/`edited`: жадный single-link по порогу
   `m3.oth_cluster_threshold`. Порог **не калиброван** (см. ограничения
   отчёта): значения сходства выводятся рядом с каждым кластером, чтобы
   читатель видел, насколько плотно он собран. Для каждого кластера пишется
   строка `code_proposal`:
   - `code_name` = `OTH_<минимальный fragment_id кластера>` — детерминированно
     и уникально в рамках интервью;
   - `definition` = объединённые `oth_description` кластера;
   - `reason` = id фрагментов и минимальное сходство внутри кластера;
   - `status = 'pending'`, `run_id` — прогон команды.

5. Повторный `propose-oth` не создаёт дублей: если `pending`-предложение с тем
   же `code_name` уже есть, строка не добавляется. Миграции и уникального
   индекса для этого не требуется.
6. Кластер из одного фрагмента — допустимый результат; он означает, что
   близких `OTH` нет.
7. В отчёте и дашборде это называется «лексическое сходство», не
   «эмбеддинги»: векторы построены по словам, а не моделью.

### Граничные случаи

| Случай | Поведение |
|---|---|
| Нет принятых аннотаций | Дашборд и отчёт строятся, все листья `no_data`, явная строка |
| Тема без кодов | `theme_codes = 0`, статус `no_data`, пометка «тема без кодов» |
| Код без темы | В список неиспользованных, в дерево не попадает |
| Код только с вопросами чужой группы | В списке неиспользованных с пометкой «не применимо к группе», не в числе применимых-но-не-найденных |
| `OTH` без `oth_description` | В кластер не входит, выводится предупреждение |
| Один `OTH` | Кластер из одного фрагмента |
| Нулевой вектор фрагмента | Сходство 0, в кластер не тянет |
| Повторный `build-vectors` с тем же `<hash>` | Векторы не пересоздаются, счётчик «пропущено» растёт, дублей нет |
| Вопрос чужой группы без ответа | В список «без ответа» не попадает |
| Цитата длиннее лимита | Префикс по границе слова + ` …` |
| Прогон не найден | Ошибка с требованием выполнить `code` |

## Макет дашборда

Дашборд отвечает на один вопрос: «где дыры в покрытии». Один файл HTML,
инлайновые стили и SVG, без JavaScript и внешних ресурсов. Пометка «эвристика,
1 интервью» стоит у статусов листьев и у блока покрытия кодбука.

### Блок 1. Дерево тем

Таблица: узел → тема. Колонки:

| Колонка | Содержимое |
|---|---|
| Статус | Плашка `нет данных` / `мало` / `есть данные`, рядом подпись «эвристика, 1 интервью» |
| Аннотаций | Число принятых аннотаций темы |
| Кодов | `различных с аннотациями / привязано к теме` |
| Покрытие фрагментов | Число и процент от всех фрагментов |
| Кривая | Мини-SVG накопления различных кодов по порядку реплик |

Темы без покрытия видны сразу: строка с плашкой `нет данных` и нулями. Под
строкой темы — `<details><summary>цитаты</summary>` с 1–2 цитатами.

### Блок 2. Покрытие кодбука

`Использовано N из 42 кодов` и один список неиспользованных кодов, без
разделения на группы. На снимке 26 неиспользованных:

- 8 E-кодов (Ошибки исполнения) помечены как «вопросы только для „ТОРГ“»
  (вопросы 9Т, 14Т-а, 14Т-б) — их отсутствие у неторгующего респондента не
  дефект;
- 18 кодов применимы к группе, но принятых аннотаций нет: Ответственность 7,
  Предупреждения 4, Основание 2, Проверка 2, Риски 2, Контроль 1.

Различие сохраняется пометкой на самом коде (пунктирная рамка и подпись под
списком), а не вторым списком: вопрос у блока один — «чего не хватает», и
разрывать ответ на две таблицы незачем. Признак `applicable` остаётся в модели
данных и считается по `question_code` → `question.group`, чтобы отсутствие
неприменимого кода не читалось как провал покрытия.

### Блок 3. Качество данных

Статусы аннотаций (`proposed` / `accepted` / `edited`), `unmarked`, `OTH`,
`skipped_garbled`, `doubtful`, распределение `reliability`, вопросы гайда без
ответа респондента (3, 14, 21 на снимке) с оговоркой про неприменимые вопросы
группы «ТОРГ». Отдельной строкой — доля принятых аннотаций на `doubtful`:
39 из 48 принятых, 33 из 106 `doubtful`-фрагментов.

### Блок 4. Цитаты

Цитаты живут внутри блока 1 под строкой темы, через `<details>`, без
JavaScript.

### Прототип до реализации

До агрегации собирается HTML-прототип на синтетических данных (без БД, без
реального текста) и показывается оператору для оценки вида. Прототип лежит в
`data/exports/prototype_dashboard.html`, в репозиторий не попадает. Агрегация
начинается только после того, как вид принят.

## Риски и зависимости

- **Лексические векторы не равны смысловым.** TF-IDF по леммам находит
  похожие формулировки, но не синонимы. Замена на модель потребует
  пересчёта `embedding` и перекалибровки порога кластера. Снижение: правило
  версионируется в `embedding.model`, отчёт называет это «лексическим
  сходством».
- **Границы статусов листьев не откалиброваны.** На одном интервью 0 / 1–3 /
  4+ — грубая шкала «есть чем показать или нет», а не измерение раскрытия
  темы. Снижение: пометка «эвристика, 1 интервью» в каждом месте, значения в
  `config.yaml`, шкала не подгоняется под красивую градацию.
- **Мало принятых аннотаций.** 48 принятых на 217 фрагментов и 16 из 42 кодов
  делают отчёт бедным. Это ограничение данных, а не рендера; давление
  возвращается в M2, а не решается здесь.
- **Статический HTML не масштабируется на корпус.** При десятках интервью
  понадобится интерактив. Снижение: агрегация и рендер в разных модулях,
  меняется только рендер.
- **Смешение этапов в одном SPEC.** Приёмка M3 откладывается до конца
  итерации. Снижение: отдельные критерии и отдельные тесты по этапам.
- Зависимость от M2: без принятых аннотаций M4/M5 бессмысленны.
- Зависимость от M1c: `question_id` и порядок реплик нужны для кривых и
  списка вопросов без ответа.

## Проверка по конституции (что из CONSTITUTION здесь критично)

- §1: код пишется после approve SPEC; прототип — артефакт для оценки вида,
  не код пайплайна.
- §2: новых зависимостей нет; лемматизация — существующий `pymorphy3`;
  HTML и SVG собираются стандартной библиотекой.
- §4: миграций нет; SQL только в `db/`; `build-vectors` идемпотентна (при том
  же `<hash>` векторы не пересоздаются и не дублируются); `propose-oth` не
  удаляет строки, а пропускает существующие `pending`.
- §5: реальные тексты только под `data/`; в логах нет текста реплик;
  артефакты в `data/exports/` и `data/reports/`.
- §6: агрегаты только по решению человека; цитаты по L2 с многоточием на
  вырезках; статусы листьев помечены как эвристика на одном интервью; тип
  расшифровки указан; сравнение групп не делается.
- §7: LLM в этой итерации не вызывается; нарратив отложен.
- §9: юнит-тесты по этапам и один сквозной на синтетике; готово только при
  зелёных `pytest`, `ruff` и типах.

## Открытые вопросы

1. **Границы статуса листа.** `0 / 1–3 / 4+` заданы в `config.yaml` как грубая
   шкала «есть чем показать тему или нет», а не как измерение раскрытия темы.
   Пересматриваются после второго интервью.
2. **Порог кластера `OTH`.** `0.35` не калиброван и в этой итерации не
   калибруется: на пяти `OTH` подгонка порога была бы подгонкой под шум.
   Сходство выводится рядом с кластерами, в ограничениях отчёта стоит «порог
   кластеризации не калиброван». Калибровка — на корпусе.
3. **Нарратив модели.** Отложен; нужен отдельный SPEC с правилом проверки
   чисел для производных формулировок.
4. **Формат docx.** Не вводится; если заказчику нужен docx, потребуется
   `python-docx` и разрешение оператора (CONSTITUTION §12).
5. **Покрытие 16 из 42 кодов.** Остаётся задачей M2; в этой итерации только
   измеряется.
