# WORKFLOW: от манифеста к коду

Цепочка: MANIFEST, PLAN, SPEC, tasks, реализация, приёмка. Каждое звено читается как контекст для следующего. Конфликты решаются по приоритету из CONSTITUTION.

| Документ | Отвечает на вопрос | Кто утверждает |
|---|---|---|
| MANIFEST | Что и зачем строим, для кого, что не входит | оператор |
| CONSTITUTION | По каким правилам работаем | оператор |
| PLAN | Из каких этапов состоит путь, в каком порядке | оператор |
| SPEC | Что именно делаем в этом этапе, как проверим | оператор |
| tasks | Какие шаги внутри SPEC | агент предлагает, оператор подтверждает |

## Цикл на каждый этап
1. Оператор или агент создаёт SPEC из шаблона. Вопросы к оператору фиксируются в разделе «Открытые вопросы» и закрываются до реализации.
2. Агент проверяет SPEC на соответствие MANIFEST и CONSTITUTION (раздел «Проверка по конституции»).
3. Агент пишет список задач с критериями завершения, оператор подтверждает.
4. Реализация по задачам, каждая закрывается тестами.
5. Отчёт, обновление `docs/DECISIONS.md`, при необходимости обновление MANIFEST/PLAN по решению оператора.

## Шаблон SPEC (`specs/_TEMPLATE.md`)
```
# SPEC-XX: название
Статус: draft | approved | done
Связь с MANIFEST: какие требования закрывает
## Цель
## Контекст и входы
## В рамках / вне рамок
## Контракты данных (таблицы, схемы JSON, форматы файлов)
## Поведение и правила (включая граничные случаи)
## Критерии приёмки (проверяемые, с командами)
## Тесты
## Риски и зависимости
## Проверка по конституции (что из CONSTITUTION здесь критично)
## Открытые вопросы
```

## Шаблон STUCK (остановка агента)
```
STUCK: краткое название проблемы
Что делал: (подходы, 1-3 пункта)
Что получилось / не получилось: (факты, текст ошибок без секретов)
Гипотеза причины:
Варианты решения: A / B (с последствиями)
Вопрос оператору: (один конкретный вопрос)
```
